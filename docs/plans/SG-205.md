## Understanding
docs/06 SG-205 asks for the extras catalogue with stock and 409 `INSUFFICIENT_STOCK` beyond it (AC1); adding extras to a stay, decrementing stock atomically, updating the quote, no change on a repeated key (AC2); check-out that records `check_out_at` from the server, freezes the quote into an invoice with a bill code and returns the same invoice on repeat (AC3); 409 `STAY_NOT_ACTIVE` for extras on a checked-out stay (AC4); the invoice equal to the matching `billCases` and a refund when the deposit exceeds the total (AC5); the room staying OCCUPIED until the invoice is paid (AC6, docs/02 §6.1: the payment-event handler of SG-302 sets TO_CLEAN). docs/04 §2.3: `listServices` OWNER and RECEPTIONIST without a building level; `addStayExtras` and `checkoutStay` need EDIT on the stay's building. SG-101 gives `pricing.Price`, `QuoteRunning` and `Assemble` (billCases are the executable spec); SG-203 gives the stay repo, `StayDetail`, idempotency wiring, request body cap and masking. Gaps found: `services` has no `code` column although the contract addresses extras by `serviceCode` (SG-203 carries the service id in `extras[].serviceCode` until now); the bill code format is only given by the contract example `PH0930A101`; invoices have no producer yet; `createdAt` defaults to `now()` in the schema, but server time must come from the injected clock.

## Interfaces (in words)
- `AddExtras` order: role, input validation, stay lookup (404), EDIT on its building (403), idempotency Begin (route includes the stay id), lock the stay row, require ACTIVE (`STAY_NOT_ACTIVE`), resolve services by code (unknown is a 422 field error), decrement each service in code order with a guarded update (zero rows means `INSUFFICIENT_STOCK`, the whole transaction rolls back), insert one `stay_extras` row per line with the unit amount copied from the service, audit, rebuild the stay view with its live quote, Complete with status 200.
- `Checkout` order: role, stay lookup, EDIT, Begin (empty body), lock the stay row; if it is already CHECKED_OUT return its invoice (also under a different key); otherwise take `check_out_at` from the clock, price check-in to check-out with `pricing.QuoteRunning` (equal to `Price` whenever check-out is after check-in; it also keeps a same-instant check-out at the minimum billable amount), add extras and deposit with `pricing.Assemble`, pick a free bill code, insert the invoice (`total` is the quote total; the amount to collect is the quote's `balanceDue`, which SG-301 reads), mark the stay CHECKED_OUT with `check_out_at`, audit, Complete with 201. The room is not touched (AC6); SG-302 owns PAID, TO_CLEAN and housekeeping.
- Bill code: `PH`, month and day in the tenant zone, the room code reduced to uppercase letters and digits (at most 8), then a counter suffix from 2 when the base is already taken; unique per tenant by the table constraint, the counter query runs under the stay lock.
- All times come from the injected clock (rule 3); money is `int64` through `money.Vnd` (rule 1); extras amounts equal quantity times unit amount (CHECK in the table); the invoice quote is stored once and never recomputed.

## Rulings (decisions needing the tech lead)
1. Size: two PRs (use cases, adapters); exceptions recorded if above 400 lines.
2. `services.code` added by migration 0007 because the contract addresses extras by code; backfill from the English name, falling back to the id.
3. Bill code follows the contract example (`PH` + MMDD + room code) with a counter suffix for repeat days on one room; transfer-note length limits of providers are not known yet (A-04), so the code stays at most 20 characters.
4. `invoices.total` holds the quote total; the payable amount is the quote's `balanceDue` (zero when a refund is due), which SG-301 must use.
5. A repeated check-out under a different key returns the existing invoice with 201 (the only declared success) instead of an error, as the story says "returns the same invoice on repeat".
6. Duplicate service codes in one extras request are merged and the merged quantity must stay within 1 to 99.
7. Invoice `createdAt` is the check-out instant from the injected clock, not the database default.
8. `FF_S3_CHECKOUT` off returns 404 `FEATURE_DISABLED` for all three operations (same pattern as the other slices).
9. The billing use cases live in a separate `Billing` type with its own constructor and its own `BillingStayRepo` port (the stay-side writes), so the SG-203 `Stays` constructor, `StayRepo` port and wiring stay untouched; the role and building check is a small `guard` shared by both types. `Billing` also takes the `Encryptor`, because the stay view it returns masks the ID number.
10. The stay-side billing writes sit behind `BillingStayRepo` (see Ruling 9). The bill code is chosen by probing exact candidates (`BillCodeTaken`, attempt 1, 2, ... up to 50, then an error) instead of counting prefixes, because a prefix count can overlap other rooms (A101 and A1011) and collide; the unique constraint stays the backstop.
