## Understanding
docs/06 SG-203 asks for server-side check-in: an ACTIVE stay, the room set OCCUPIED, `check_in_at` from the server clock and a rate plan snapshot (AC1); one winner among concurrent check-ins of a vacant room, the loser gets 409 `ROOM_NOT_VACANT` (AC2); idempotent replay by `Idempotency-Key`, a different body gives 409 `IDEMPOTENCY_KEY_REUSED` (AC3); an optional ID number stored encrypted, returned masked, never logged (AC4); deposit stored and returned on every stay response, no cash drawer entry here (AC5); `GET /v1/stays/{id}` returns a live quote equal to the engine's result for the same instants (AC6). docs/04 §2.3 gives the matrix (createStay EDIT, getStay VIEW, roles OWNER and RECEPTIONIST); docs/05 §3 fixes AES-GCM with an environment key and masking on read; docs/10 §0 and §4 name an `Encryptor` port and demand a fail-fast missing key; ADR-006 and SG-101 give the pure pricing engine and bill assembly. Gaps found while reading: no `Encryptor` port, adapter or `DATA_ENCRYPTION_KEY` config exists yet (api/CLAUDE.md already promises the fail-fast start); `stays` has no `guest_phone` column although the contract requires it; the idempotency store exists but nothing wires it (its comment hands bounds on key, route and body to the wiring); SG-101 Ruling 7 requires a snapshot schema version before snapshots are stored by this story.

## Interfaces (in words)
- Order in `CreateStay`: role check, parse and validate body, room lookup (404) and building level (403) as in SG-201, then open the unit of work: idempotency Begin (route string includes the concrete room id so one key cannot replay another room's stay), lock the room row, require VACANT, parse the unit type's plan with `ParseRatePlan` (an invalid stored plan is a server error, never a client one), encrypt the id number, insert the stay with the canonical snapshot and schema version, set the room OCCUPIED, audit, build the response, Complete the key with status and body, commit. A losing concurrent request blocks on the key or the room lock, then sees a replay or a non-vacant room.
- `GetStay` reads the stay with its extras and the room's building, checks role and level, prices with the injected clock via `pricing.Price` and `pricing.Assemble` (pure domain, no port). Times only from the server clock (rule 3); money `int64` through `money.Vnd` (rule 1).
- Responses never carry the full id number. Errors never echo input. `Encryptor` fails closed (an undecryptable value is an error, not an empty string).

## Rulings (decisions needing the tech lead)
1. Size: three PRs (foundations, use cases, adapters) because the story also builds the missing encryption seam and the first idempotency wiring; each PR expected near the 400 line limit, exceptions recorded if above.
2. Encryption: AES-256-GCM, key from `DATA_ENCRYPTION_KEY`, ciphertext prefixed with a key version byte (single key now, rotation later), additional data binds tenant and field so values cannot be swapped across tenants or columns. No new dependency (standard library).
3. SG-101 Ruling 7 resolved by a separate `stays.rate_plan_schema` column instead of changing the snapshot bytes (SG-201 readers parse the canonical plan directly).
4. Masking shows the last 3 characters only for ids of 8 or more characters; shorter ids (including every valid 5 to 7 character id) give only five asterisks; length is not revealed.
5. Input limits (name 120, phone 6 to 20, id 5 to 20, deposit maximum a named constant) follow the contract and are enforced again in the domain.
6. Idempotency route key includes the room id; replays are tenant scoped, so another user of the same tenant replaying the same key gets the stored response after passing authorization.
7. Flag `FF_S2_CHECKIN` off returns 404 `FEATURE_DISABLED` for both operations, the same pattern as `FF_S1_ROOM_MAP`.
8. `getStay` returns extras read from `stay_extras` (empty until SG-205) so the quote cannot silently omit them later.
9. The idempotency request hash fingerprints the ID number with a keyed digest (`Encryptor.Fingerprint`) because a plain hash of a low-entropy ID number would be brute-forceable from the idempotency table, defeating the encryption. The encrypted value itself is bound to its stay by the field name `stays.id_number/<stay id>`; the fingerprint uses the plain field name because the stay does not exist yet. The fingerprint is taken over the trimmed value and only when it is non-empty, so a missing, empty or whitespace-only id number hash alike (a retry switching between them replays); every other field hashes raw. An empty or over-64-byte idempotency key is rejected with `app.ErrInvalidIdempotencyKey` before any I/O (PR 3 maps it to 422).
10. The stored idempotency response body is the JSON of the app-level stay detail view (never the plain ID number), and the handler maps a fresh or replayed view to the contract type the same way, so replays are identical. The type is `StayDetail` because `StayView` already names the room map's compact active stay.
11. `pricing.QuoteRunning` now holds the minimum-billable rule shared by SG-201's quoter and `getStay`.
12. Known limit: the generated strict decoder accepts unknown JSON fields and trailing data although the contract says `additionalProperties: false`; left as is, a contract-level fix would regenerate the decoder. Request bodies are capped at 64 KiB for every route.
