## Understanding (cites docs sections)
SG-001 (docs/06) gives every lane one green baseline: a Makefile with the seven named targets, a Go module with chi and `GET /healthz` that logs the fields of docs/02 §7.6, a Next.js static-export placeholder served by the same API container (docs/02 §8: one container on 8080), PR CI (lint, unit tests, gitleaks full history, licence check), pinned dependencies with automated updates, Apache-2.0 `LICENSE` and `NOTICE` (ADR-002), and Claude Code read-deny rules (docs/11 §4 rule 14). Layout and lane ownership follow ADR-001; stack names follow docs/02 §9, where versions are "pinned in SG-001". Commits follow docs/10 §11. No contract, migration or pricing change is involved. The Dockerfile and Compose are PLAT files under `deploy/` (CLAUDE.md §1), and `make up` needs them for AC3.

## Interfaces in words
- `GET /healthz`: no auth, 200 with a small JSON body `status` = `ok`; never touches the database (readiness arrives with `/readyz` in SG-003).
- Request log line, one per request, JSON: `trace_id`, `tenant_id`, `user_id`, `route`, `status`, `duration_ms`, constant message. `route` is the chi route pattern, not the raw URL, so paths never carry personal data. `tenant_id` and `user_id` are empty strings until SG-102 supplies them. `trace_id` is taken from `X-Request-Id` when valid, else generated.
- Static handler: serves files from the configured directory; unknown paths return the web `404` page; never serves `/healthz` or API routes.
- Config: `PORT` (default 8080), `STATIC_DIR`, `LOG_LEVEL`; invalid values fail at startup with a clear error.

4. Release notes: tooling is not user-visible; propose no Unreleased entry.
5. AC6 syntax (official docs, https://code.claude.com/docs/en/permissions, section on Read and Edit rules): `Read(path)` deny rules use gitignore patterns; `Read(./dir/**)` is relative to the project root, `//path` is absolute, and a Read deny also blocks Edit and Write on the same path. Deny rules cover Claude's file tools and recognised Bash file commands (`cat`, `head`, `sed`) but not arbitrary subprocesses or `grep -r`; OS-level sandboxing is the stronger option and is out of scope. Planned denies: `api/internal/**/gen/**` style generated stubs (exact path set by SG-002), `web/src/api/generated/**`, `**/node_modules/**`, `**/vendor/**`, `web/out/**`, `web/.next/**`, `**/dist/**`, `**/*.lock` and `package-lock.json`, `contracts/pricing/golden-cases.json`, `coverage/**`. The generated-code paths are best guesses until SG-002 fixes them; the plan reserves a one-line update in SG-002. The `.claude/settings.json` location is my reading of the docs, to be re-verified in task 11.

## Risks and rollback
- Version drift between this plan and install time: mitigated by the re-check in the tasks note.
- Next.js static export plus the API fallback handler may hide real 404s: tested in task 4.
- CI actions pinned by SHA need manual SHA lookup: Dependabot keeps them fresh.
- Broad deny rules could block needed reads (for example lockfile diagnosis): rules are path-specific and editable in one file.
- Rollback: the story is one squash-merged PR; revert it. The planted-secret branch is never merged.
