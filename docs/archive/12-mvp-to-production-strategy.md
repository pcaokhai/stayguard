# 12 - MVP to Production Strategy & Architectural Review

## 1. Context & Objective
The StayGuard project is a portfolio/PoC designed for small guesthouse anti-loss management. 

### 1.1 Current Progress & Why it is slow
- **Backend (Go):** Core foundation is implemented (Database, Pricing Engine, Sessions/Identity, Room read APIs, and Check-in API).
- **Frontend (Next.js):** Currently at 0% implementation (everything is in the Backlog).
- **Why is it slow?** The backend was built with a highly robust, enterprise-grade architecture (Hexagonal, AES Encryption, RLS, Idempotency, 100% Test Coverage). While excellent for a mature, hyper-scale product, this level of strict engineering creates immense friction and acts as a massive bottleneck for a startup needing to launch a rapid MVP/Demo in a matter of days. The frontend was also bottlenecked by the initial plan to write all Tailwind CSS manually from scratch.

### 1.2 User Base Analysis & Scalability
This application targets **small guesthouses**, meaning the concurrent user base per tenant will be extremely low (1-5 front desk staff/owners per building). 
Because the user base is small, hyper-scalability, microservice-level abstractions, and strict database row-level security (RLS) are **not strictly necessary** for the MVP. The tech choices must prioritize rapid development speed now, while ensuring the architecture can handle standard scaling later. 

This document captures a comprehensive architectural review and establishes a pragmatic strategy: **Accelerate the MVP delivery by stripping away over-engineered infrastructure temporarily, while retaining the exact UI/UX design requested by the customer, and defining a clear roadmap back to production-grade standards.**

## 2. Comprehensive Architectural Review & Bottlenecks

### 2.1 Backend (Go) - The "Over-engineering" Bottleneck
The current API is built using **Hexagonal Architecture (Clean Architecture)**. It features:
- Domain, App (Use Case), and Adapter layers.
- Strict PostgreSQL Row-Level Security (RLS) via tenant-scoped transactions.
- Idempotency stores to prevent double-billing.
- AES-256-GCM encryption for Personally Identifiable Information (PII).
- Testcontainers and 100% test coverage requirements.

**Bottleneck Analysis:** This is a masterclass in Go backend design, but for a 3-to-5-day MVP sprint, it is a massive bottleneck. Implementing a simple CRUD endpoint requires touching 4 different files, writing interfaces, mapping domains, and setting up Docker tests. 

### 2.2 Frontend (Next.js) - The UI Fidelity Challenge
The initial plan (ADR-011) called for Next.js App Router (Static Export) and building Tailwind CSS components from scratch.
**Bottleneck Analysis:** Building UI from scratch is too slow. However, we possess high-fidelity UI code (Tailwind/React) already generated by **Claude Design** that perfectly matches the client's visual requirements. Forcing all of this into a generic component library (like MUI or Bootstrap) would ruin the design language.

## 3. Tech Choices & Accelerated MVP Strategy (Trade-offs)

To launch the demo rapidly, we accept technical debt intentionally. We choose technologies that offer maximum speed now but can be refactored easily later:
- **Backend Options & Frameworks:** Starting from zero, utilizing high-level frameworks (like **Gin, Fiber, or Echo**) alongside ORMs (like **GORM or Ent**) significantly speeds up routing, request binding, and DB migrations compared to standard library `net/http` and raw SQL. However, since this project already has `sqlc` configured with typed `openapi-fetch` handlers, ripping it out to install Gin/GORM would *waste* time. The fastest path is to **keep the current stack (pure Go + sqlc)** but completely flatten how it is used (ignoring Clean Architecture).
- **Frontend Options:** Next.js + Tailwind is the optimal stack to leverage the existing Claude Design code, supported by selective `shadcn/ui` imports.
- **AI Guidance:** AI assistants (like Claude Code) must be instructed to bypass standard enterprise rules during the MVP phase.

### 3.1 Backend Trade-offs (Speed over Purity)
For all new endpoints required for the MVP (e.g., Housekeeping, Checkout):
1. **Flatten the Architecture:** Bypass the `domain` and `app` layers. Write business logic and `sqlc` database queries directly inside the HTTP Handlers (`adapter/http`).
2. **Defer Security Overhead:**
   - **No RLS:** Stop configuring Row-Level Security policies in migrations. Use simple `WHERE tenant_id = ?` in SQL queries.
   - **No Encryption:** Save PII (like ID numbers) as plaintext in the database for the demo.
3. **No Idempotency at Backend:** Do not implement the `Idempotency-Key` logic for new endpoints. Prevent double-submissions via the Frontend UI (e.g., disabling the submit button).
4. **Halt Automated Testing (Testing Strategy):** 
   - Stop writing Unit Tests, Integration Tests (Testcontainers), and Playwright E2E tests.
   - **MVP Testing Protocol:** Rely entirely on **Manual Testing**. Test APIs via Postman or Swagger UI. Test the Frontend by clicking through the "Happy Path" using the MSW mock UI or connected to a local database. Fix bugs directly on production/staging if they arise during the demo phase.

### 3.2 Frontend Trade-offs (Hybrid UI Approach)
1. **Maximize Claude Design Code:** Reuse the raw Tailwind/React code generated by Claude Design for all static layouts, cards, typography, and basic buttons. This guarantees 100% adherence to the original design without writing CSS.
2. **Selective `shadcn/ui`:** Do not force everything into a library. Use `shadcn/ui` (via CLI `npx shadcn@latest add`) **only** for complex, interactive, stateful components (e.g., Modals, DatePickers, Selects). This saves days of debugging accessibility and state logic.
3. **Direct Integration (Skip Scaffolding):** The AI workflow should skip building "Dumb UI". Instead, run `npm run gen:mocks` to generate MSW mocks, and instruct the AI to immediately bind `openapi-fetch` and `TanStack Query` to the existing Claude Design UI code.
4. **Hardcode Infrastructure:** Hardcode the 'Owner' role, bypass the Role Picker, and ignore i18n (multi-language) setup. Render the app in the primary language only.

### 3.3 CI/CD & Code Review Trade-offs
The current `.github/workflows/ci.yml` and project policies are heavily restrictive, acting as severe bottlenecks for rapid AI-assisted development.
1. **Remove PR Size Limits:** The rule (from `docs/10 §143`) limits PRs to 400 lines. AI generation (especially UI code) can easily produce 1,000+ lines in minutes. Forcing developers to split functional MVP code into multiple PRs solely to pass a line-count check wastes immense time. **Action:** Ignore PR size limits for the MVP.
2. **Halt CI Integration Tests:** The `test-api-int` job in CI spins up Testcontainers (PostgreSQL via Docker). Since automated testing is halted (Section 3.1), this CI job only consumes build minutes and blocks merging. **Action:** Comment out `test-api-int` in `ci.yml`.
3. **Disable Contract Breaking Checks (`oasdiff`):** The `contracts` CI job uses `oasdiff` to prevent breaking changes in `openapi.yaml`. In a startup MVP, breaking changes are normal and required to adapt the API to the UI rapidly. **Action:** Disable `oasdiff` checks in CI.
4. **Disable License Audits:** The `licenses` job checks third-party dependency licenses. This is an enterprise compliance step, irrelevant for a 3-day MVP demo. **Action:** Disable the `licenses` job in CI.
**MVP CI Pipeline:** The CI should only contain: Linting/Formatting, Gitleaks (Secrets scanning), and Build checks (`go build` & `npm run build`).

### 3.4 Extreme Startup Shortcuts ("Move Fast & Break Things")
If the goal is to win the project at all costs and speed is the only metric that matters right now, eliminate these additional structural bottlenecks:

1. **Abolish Feature Flags (`FF_S1_ROOM_MAP`, etc.):** The codebase currently gates every story behind a feature flag (returning `404 FEATURE_DISABLED`). For a 1-to-2 person startup team, trunk-based development with feature flags is pure overhead. **Action:** Delete feature flag logic. Commit directly to `main` and deploy. If a feature isn't ready, just don't link it in the UI.
2. **Stop Hand-Writing OpenAPI YAML:** Contract-first design is great, but writing `openapi.yaml` manually is slow. **Action:** Do not write YAML by hand. Prompt Claude Code to generate the OpenAPI YAML additions for you based on the desired UI, then simply run `make gen` to get your Go/TypeScript types instantly.
3. **Drop Server-Sent Events (SSE) for Polling:** The architecture specifies SSE for real-time payment updates. SSE introduces complex connection management, dropped connections, and Goroutine leaks. **Action:** For the MVP, use **HTTP Polling**. TanStack Query has a built-in `refetchInterval: 3000`. It takes 1 line of code on the frontend and zero complex Hubs on the backend.
4. **Abandon Custom Value Objects:** The domain rules state "Money is `int64` whole VND wrapped in a `Vnd` type with checked arithmetic." **Action:** For the demo, just use primitive `int64` for money. Avoid writing custom wrapper types and arithmetic methods until the startup is actually processing real financial transactions at scale.
5. **Split Deployment (Vercel + Railway/Render):** The current plan (SG-603) involves embedding the Next.js static export inside the Go binary. This requires custom Dockerfiles and routing logic. **Action:** Don't build custom deployment pipelines. Deploy the `web` folder to **Vercel** (zero-config) and the `api` folder to **Railway or Render** (auto-detects Go). You will have a live URL in 5 minutes.

### 3.5 AI Prompting & Token Optimization Strategy (For Future Review)
The current rules in `api/CLAUDE.md` and `web/CLAUDE.md` contain strict constraints that waste AI tokens (context window limit) and drastically slow down code generation. 
*Note: These updates are documented here for future review by Codex/Claude Desktop before being directly applied to the `CLAUDE.md` files.*

#### A. Backend Prompting Override (`api/CLAUDE.md`)
The override should instruct the AI to bypass strict enterprise patterns:
- **Skip Hexagonal Layers:** Write business logic and DB queries directly in `adapter/http`.
- **Skip Tests:** Explicitly command the AI *not* to generate tests.
- **Skip Security Overhead:** Tell the AI to ignore RLS, AES Encryption, and Idempotency logic for new endpoints.
- **Skip Custom Value Objects:** Tell the AI to use primitive types (`int64`) instead of wrapped types (`Vnd`).

#### B. Frontend Prompting Workflow (`web/CLAUDE.md`)
The workflow should enforce a direct integration approach rather than from-scratch scaffolding:
1. **Selective Component Strategy:** Do not blindly replace existing Claude Design Tailwind code with `shadcn/ui`. Paste the pre-generated Claude Design code directly into page components. Only run `npx shadcn@latest add` for interactive logic (complex forms, dialogs).
2. **Mandatory Code Generation:** Never write `fetch` wrappers manually. Run `npm run gen:api` to generate `openapi-fetch` client, and `npm run gen:mocks` for `msw`.
3. **Direct Integration Prompting:** When assigning a screen ticket to Claude, skip the "Dumb UI" creation step. Prompt exactly: *"Run `npm run gen:mocks` to understand the data shape. Take the existing Tailwind UI code provided and use `openapi-fetch` and `TanStack Query` to connect it to the actual backend endpoints."*

## 4. Roadmap to Production (Post-Demo) & Architecture Necessity

Once the MVP is validated, we must evaluate which parts of the "Enterprise-Grade Architecture" are actually worth reviving for production.

### 4.1 Is Enterprise-Grade Architecture Necessary for this App?
This app targets **small guesthouses (10-30 rooms, 1-5 staff members per tenant)**. It is not an ultra-high-frequency trading platform or a massive consumer social network. 
- **Hexagonal Architecture:** **Unnecessary.** For an app dominated by basic CRUD operations (Check-in, Check-out, Edit Room), mapping data across 3 separate domain/app/adapter layers creates massive overhead. A standard MVC or layered approach (Router -> Service/Handler -> DB) is perfectly adequate for production.
- **100% Test Coverage:** **Unnecessary.** Maintaining 100% test coverage drastically slows down iteration. For production, targeting ~70% coverage focused *only* on the critical paths (Pricing, Invoicing, Authentication) is the industry standard for startups.
- **Row-Level Security (RLS):** **Recommended but Optional.** While a simple `WHERE tenant_id = ?` query works, RLS is a powerful defense-in-depth mechanism for SaaS apps to prevent cross-tenant data leaks. It's worth re-enabling for production, but not critical for the first 100 paying customers.
- **Idempotency:** **Highly Recommended.** Double-charging a customer because a receptionist double-clicked "Checkout" is a fatal UX error. This should be reinstated for production billing endpoints.
- **AES-256-GCM Encryption for PII:** **Overkill (Unless Compliance Requires It).** Unless the app is storing credit card numbers (which it shouldn't) or full National ID images, application-level AES encryption is overkill. Standard Cloud Provider Encryption at Rest (e.g., AWS RDS encryption) is sufficient for phone numbers and names.

### 4.2 Realistic Production Phases
**Phase 1: Win the Demo (Current Focus)**
- Deliver visual perfection using Claude Design code.
- Functional endpoints using flattened Go handlers (MVP Mode).
- Deploy to Vercel (Frontend) and Cloud Run/Railway (Backend).

**Phase 2: Stabilization (First 1-10 Paying Customers)**
- Re-implement Idempotency for Checkout/Payment endpoints.
- Write Integration Tests for the Billing engine only.
- Complete the Next.js `messages/` internationalization (i18n).
- Replace hardcoded Auth with real tenant/role sessions.

**Phase 3: Scale (100+ Customers)**
- Re-enable PostgreSQL RLS policies to guarantee data isolation.
- Refactor the most complex flat HTTP handlers into a Service layer (but do not force strict Hexagonal pure-domain rules).

## 5. Impact Analysis: Applying this Strategy as a 1-Person Startup

Since you are a **solo developer (1-person startup)** building a product for a relatively simple domain (guesthouse management), adopting the "Extreme Startup Shortcuts" will have significant impacts on the existing codebase. 

### 5.1 The "Split-Brain" Codebase (Negative Impact)
- **The Reality:** The codebase currently has a solid foundation (Pricing, Check-in, Identity) written in strict Hexagonal Architecture. If you start writing new features (Checkout, Housekeeping) using flat HTTP handlers, your codebase will become inconsistent ("split-brain").
- **The AI Risk:** Claude Code learns by observing existing patterns. If it sees `app/stays`, it will naturally try to create `app/housekeeping`. 
- **Mitigation:** You must be extremely explicit in your prompts. You have to force Claude to ignore the existing folder structure and write "ugly but fast" code.

### 5.2 Speed & Delivery (Massive Positive Impact)
- **Current State:** Implementing a feature end-to-end (DB -> Repo -> Domain -> Use Case -> Handler -> Testcontainers -> OpenAPI -> Frontend) currently takes a solo dev + AI about 2-3 days per feature.
- **New State:** By bypassing Hexagonal layers, tests, and CI bottlenecks, you shrink the surface area of a feature to just 2 files: `openapi.yaml` and `handler.go`. Time-to-delivery drops to **2-3 hours per feature**. This is the only way a solo founder can deliver a full Demo in a week.

### 5.3 Security vs. Pragmatism (Calculated Risk)
- **RLS & AES Encryption:** Dropping Row-Level Security and AES encryption introduces technical risk in a mature SaaS. However, as a solo founder seeking product-market fit, your biggest risk is *building something nobody wants*, not a data breach of 3 mock users. Standard PostgreSQL with `WHERE tenant_id = ?` is how 99% of solo startups begin.
- **Idempotency:** Dropping backend idempotency means you are fully relying on the Frontend Next.js UI (disabling the "Submit" button) to prevent double-charging. This is a calculated risk acceptable for a Demo, but must be fixed before real Stripe/Bank integrations go live.

### Conclusion for Solo Founder
To win as a 1-person startup, you must fight the urge to "engineer perfectly". The existing architecture is beautiful, but it was designed for a team of 10+ engineers to collaborate safely. For you, the proposed strategy is not just an option—it is a **survival necessity** to launch the MVP without burning out.
