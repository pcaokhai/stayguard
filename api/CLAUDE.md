Go modular monolith: REST and SSE API, business rules, multi-tenant PostgreSQL access, and it serves the embedded web export. Lane: **API**. Owns `api/**`, the database schema `app` and migrations in `api/migrations/`. Read the root `CLAUDE.md` first.

## Commands

`make test-api` (unit), `make test-api-int` (Testcontainers), `make lint` (golangci-lint, gosec, govulncheck), `make fmt`, `make gen` (oapi-codegen and sqlc), `make migrate` (runs `stayguard migrate`; needs `DATABASE_URL`), `make up` (API plus PostgreSQL; local dev connects as the owner superuser with trust auth, so RLS is bypassed). While iterating, run one test by name and pipe to `tail -n 20`. Created by SG-001, SG-002 and SG-003.

## Layout

```
api/
  cmd/stayguard/        wiring only: config, dependency construction, server start
  internal/
    domain/             pure rules, no I/O: pricing, room, stay (`domain/stay`: input validation, id masking), payment, access, shift
    app/                use cases and ports: sessions, trials, stays, payments, housekeeping, owner, shifts
    adapter/
      http/             generated strict handlers, problem+json mapper, SSE hub
      postgres/         pool, unit of work (tenant per transaction), idempotency store, audit writer, readiness probe, goose `Migrate`; sqlc queries in `queries/`, output in `sqlcgen/`
      payments/         PaymentSource port: simulator now, provider later; QR payload builder
      clock/ ids/ crypto/   time, id and encryption ports
    platform/           config, logging, metrics, rate limiting, embedded web assets
  migrations/           goose SQL, forward-only
  gen/                  generated by `make gen` (oapi-codegen v2.8.0 strict server), committed, Read-denied; never hand-edit. Stubs live in `server_stubs.go`: replace the stubs of your operations, do not embed a default
```

## Rules for this service

- An import-boundary test enforces `domain` → nothing, `app` → `domain`, `adapter` → `app` and `domain`. `cmd` is the only place that wires adapters.
- The HTTP handlers only translate: parse the request, call one use case, map the result. No business rules in handlers.
- Every use case takes the caller (tenant, user, role, building access) from the context set by the auth middleware; repositories require a tenant-scoped transaction.
- Server-Sent Events: one hub per process, bounded buffers, drop slow clients, close on terminal state, heartbeat every 15 s; goroutines are owned by the hub and stop on shutdown.
- Configuration is typed and validated at start; missing `DATA_ENCRYPTION_KEY` (standard base64 of exactly 32 bytes; `make up` creates a local one in `deploy/.env.local`) or `DATABASE_URL` stops the server; `stayguard migrate` does not need the key. Other database settings: `MIGRATE_DATABASE_URL` (owner role for `migrate`, defaults to `DATABASE_URL`) and `IDEMPOTENCY_TTL` (default 24h). The server refuses to start as a superuser, BYPASSRLS, table-owner or member-of-such role; `ALLOW_PRIVILEGED_DB=1` lifts that for local dev only.
- The server connects as the application role (no BYPASSRLS, no DDL); only `stayguard migrate` uses the owner role and migrations never run at request time. `/readyz` is 503 until every embedded migration is applied.
- Room map (SG-201): `FF_S1_ROOM_MAP` (bool, default false, invalid value stops startup) gates `listBuildings`, `listRooms` and `getRoom`; off returns 404 `FEATURE_DISABLED` before any use case or room I/O. Building access is stored (L-A2, migration 0010, `building_permissions`) and loaded into the `Caller` on every request, so a change applies on the next call; `permissions.Stored` adds the owner's implicit EDIT. A new building starts with no staff access; demo users get EDIT on every building when they are created. The running total comes from `pricing.Quoter`, which prices each stay's own rate plan snapshot with `domain/pricing`.
- PIN sign-in (L-A1, migration 0009): `signIn` is public and resolves the tenant from `tenants.guesthouse_code` through the `tenants_signin_lookup` policy (`app.signin_code`, like the session lookup). PINs are bcrypt hashes in `pin_credentials`; five wrong PINs in 15 minutes lock for 15 minutes and raise an `ACCOUNT_LOCKED` alert and write an audit row. Failure counts commit even when the answer is an error (the use case returns the error after the transaction). A user with `must_change` may call only getMe, changeMyPin and signOut (403 `PIN_CHANGE_REQUIRED`, enforced in `auth.go`). PINs are bcrypt (cost 12) over an HMAC-SHA256 of the PIN keyed by a pepper derived from `DATA_ENCRYPTION_KEY` (hash prefix `p1$`); older plain hashes verify and are upgraded on the next successful sign-in. Rate limits (per IP and per guesthouse code, in memory) are checked before any bcrypt work, and `Auth` caps concurrent bcrypt at 4 (429 above it). The failure counter is updated under a row lock and committed with `context.WithoutCancel`. A MANAGER cannot reset, lock, unlock, update or remove an OWNER or another MANAGER (`Staff.guardTarget`). `TRUST_PROXY=1` with `TRUSTED_PROXY_HOPS` (default 1) takes the IP from `X-Forwarded-For` counted from the right: single Caddy only, see `deploy/README.md`.
- Staff (L-A2, migration 0010): staff are users with a `staff_profiles` row (the owner has none and is not listed). `createStaff` returns the one-time PIN once; its idempotent replay returns the staff member without it, and `resetStaffPin` takes no idempotency key (a retry issues a new PIN). `removeStaff` needs the owner's PIN (wrong PINs count towards the lock) and asks `app.OpenShifts`, wired to `noOpenShifts` until L-B2 provides shifts. The role table in `domain/access` follows each operation's `x-access`; `TestAuthorizer_SG1101_AC2_TableMatchesContract` keeps them in step.
- Bank and SePay (L-A3, migration 0011): receiving accounts live in `bank_accounts` (number encrypted with the id bound in; keyed fingerprint rejects duplicates); the QR pays only the tenant's default account, which must be CONNECTED (`PaymentRepo.DefaultBankAccount`); a new account is PENDING and becomes default only after the installer connects it (`stayguard sepay set-secret`), or by `makeDefaultBankAccount` once connected. Adding, defaulting and removing accounts need the owner's PIN again (`Auth.requireOwnerPin`). The installer CLI (`stayguard tenant import|sepay webhook|set-secret|status`, `cmd/stayguard/installer_cli.go`) follows docs/runbooks/sepay-handover.md, runs as the application role through the unit of work, reads the secret from a terminal only and writes an INSTALLER audit row plus a SEPAY_UPDATED alert. The webhook tenant lookup policy is `tenants_hook_lookup` (`app.hook_id`). The SePay webhook is `POST /v1/webhooks/bank/{hookId}`, a raw-body handler (`webhook_handler.go`, registered after the generated routes): tenant by hook id, `X-SePay-Timestamp` within 300 s, `X-SePay-Signature` = `sha256=` + hex HMAC-SHA256 of `{timestamp}.{raw body}` with the tenant's secret, constant-time compare, 401 with no detail on any failure, 404 for an unknown hook; it answers `{"success": true}` and a retry of the same SePay `id` gets the same answer. Only `transferType: in` to one of the tenant's own accounts reaches `Payments.Settle`; outgoing transfers and other accounts' money are stored UNMATCHED without an alert. SePay's `code` field is ignored: the bill code is found inside `content`. The old single-path webhook answers 410.
- Setup (L-A4, migration 0012): `app.Setup` holds buildings, floors, rooms, rate plans and items. Rooms are retired, never deleted (`units.retired`; the map, cleaning list and check-in skip them). A room with a guest answers 409 `ROOM_OCCUPIED` to type change, maintenance and retire. A rate plan edit saves a new version for later check-ins; stays keep their snapshot. `previewPrice` runs `domain/pricing` with the tenant's time zone. Stock changes only with a row in `stock_movements` beside it (opening, restock, sale, stocktake count), so `stock = sum(movements)`; `stock_movements` is append-only for the app role. An item that is not on sale is hidden from the front desk list and from extras; the owner and manager see it, with latest cost and 7-day sales that the desk never gets. `removeService` deletes an item never sold (its movements cascade) and otherwise stops selling. A stocktake sets stock to the counted quantities with COUNT movements and raises one STOCKTAKE_DIFFERENCE alert.
- Guest ID (F-A2, migration 0018): numbers and photos live in `guest_ids` and `guest_id_photos`, read only by `postgres.GuestIDRepo` (stay queries carry yes/no `EXISTS` indicators; `stays.id_number_enc` is gone). Number and photos are AES-GCM encrypted with the stay id bound in. A photo goes through `adapter/images` (JPEG or PNG up to 5 MB, EXIF orientation applied, metadata dropped, re-encoded as JPEG, 30 MP cap); only the photo upload route may carry a body over 64 KiB. Writes are front desk with EDIT on the building; reads, reveal, view, download and delete are OWNER and MANAGER (a manager needs VIEW on the stay's building), each audited as `GUEST_ID_*` with ids only, and every `/guest-id` response is `Cache-Control: no-store`. Number and photos can be added for the active stay and for 24 hours after check-out. They are collected under the stay-declaration duty, not consent: no consent is asked, the legacy `idConsent` and `consent` fields are ignored, and the record carries `legal_basis = STAY_DECLARATION` (migration 0022). The daily retention job runs as `stayguard jobs run` (cron): `app.job_tenant_ids()` (a narrow SECURITY DEFINER function, ids only, executable by the application role only; the `tenants_job_scan` policy opens only while that function runs) lists the tenants, and each job then runs in a normal tenant-scoped transaction (`cmd/stayguard/jobs.go` is the registry; recurring expenses and leave-to-TAKEN can be added there). Guest ID retention deletes data past `idRetentionDays` and writes `GUEST_ID_RETENTION_DELETED`.
- Deleting `deploy/.env.local` orphans locally encrypted data: the old key is gone and those values cannot be decrypted.
- Check-in (SG-203): `FF_S2_CHECKIN` (bool, default false, invalid value stops startup) gates `createStay` and `getStay`; off returns 404 `FEATURE_DISABLED` before any use case. Wired in `cmd/stayguard/wire.go` (`newStays`: `postgres.StayRepo`, `permissions.Derived`, `crypto.NewAESGCM` from `DATA_ENCRYPTION_KEY`, the shared idempotency store and audit writer). Sensitive fields go through `app.Encryptor` (AES-256-GCM in `adapter/crypto`, additional data binds tenant and field). `createStay` is idempotent by `Idempotency-Key` with the route key `POST /v1/rooms/<roomId>/stays`; one winner per room comes from the room row lock, backed by the `stays_one_active_per_unit` index (both give 409 `ROOM_NOT_VACANT`). The 422 body carries `errors[]` (field and code only), mapped in `problem.go`.
- Check-out (SG-205): `FF_S3_CHECKOUT` (bool, default false, invalid value stops startup) gates `listServices`, `addStayExtras` and `checkoutStay`; off returns 404 `FEATURE_DISABLED` before any use case. The use cases live in `app.Billing` (separate from `Stays`). Extras are addressed by `services.code` (migration 0007); stock is decremented by a guarded UPDATE (`stock >= qty`), zero rows is `stay.ErrInsufficientStock`. Check-out freezes the quote into `invoices` with a bill code (`domain/invoice`); the room stays OCCUPIED until payment (SG-302). Wired in `cmd/stayguard/wire.go` (`newBilling`: `postgres.BillingRepo`, `postgres.ServiceRepo`, `permissions.Derived`, the same `crypto.NewAESGCM` encryptor as check-in, the shared idempotency store and audit writer). Routes for idempotency: `POST /v1/stays/<id>/extras` and `POST /v1/stays/<id>/checkout`; both lock the stay row (`FOR UPDATE OF s`), so extras and check-out on one stay serialize, and a repeated check-out under any key returns the one invoice (201). Bill code: `PH` + MMDD in the tenant zone + the room code reduced to uppercase letters and digits (at most 8), then a counter suffix from 2 when taken; a unique violation on `(tenant_id, bill_code)` is `app.ErrBillCodeConflict` and the use case retries up to 3 times. `invoices.quote` is the camelCase `QuoteView` JSON (keys pinned by json tags and `TestFrozenQuoteJSONKeys_SG205_AC5`: asOf, stayAmount, extrasAmount, total, depositPaid, balanceDue, refundDue, capped, lines) that SG-301 reads; `invoices.total` is the quote total; the payable amount is `quote.balanceDue` (zero when a refund is due). 409 `INSUFFICIENT_STOCK` and 409 `STAY_NOT_ACTIVE` are mapped in `problem.go`.
- Demo routes (`/v1/demo/*`): the generated route always exists but returns 404 `DEMO_DISABLED` before any I/O when `DEMO_MODE` is off (default). Session settings: `DEMO_MODE`, `SESSION_TTL_HOURS` (default 12), `TRIAL_TTL_HOURS` (default 24). The auth middleware protects every `/v1` path except `POST /v1/demo/sessions` and `POST /v1/webhooks/bank`. **Deploy gate: keep `DEMO_MODE` off in any public deploy until SG-601 (rate limit and trial cleanup) is merged.**

## Domain rules

- Money is `int64` whole VND wrapped in a `Vnd` type with checked arithmetic.
- Pricing implements docs/02 §7.7 exactly and passes `contracts/pricing/golden-cases.json`; it receives instants and a rate plan, never the clock or the database.
- Room row lock for check-in; invoice row lock for settlement; one transaction per command; no network calls inside a transaction.
- Payment matching: bill code plus exact amount plus PENDING status; anything else is MISMATCH or UNMATCHED and raises an alert; duplicates are acknowledged and ignored.
- Room status transitions live in one function; OVERDUE is derived, not stored.
- Sensitive fields (ID number, bank account number) are encrypted through the crypto port and never logged.

## Go rules

Follow docs/10 §4.2. Notably: `ctx` first, wrap errors with `%w`, typed errors mapped in one place, no `panic` outside `main`, small consumer-side interfaces, table-driven tests, `goleak` on long-running components, no package named `util` or `common`.

## Database

- Every new table lives in schema `app`, enables and forces RLS with a `tenant_id` policy through `app.current_tenant()`, and gets its own grants in the migration that creates it. The RLS coverage test fails otherwise.
- A new table also needs a fixture in the isolation catalog (`isolation_fixtures_test.go`) so TS-08 covers it; add the queries to `queries/` and run `make gen`.
- Migrations are forward-only goose files numbered in order; never edit an applied one.

## Tests

Names end with the story and criterion, for example `TestCheckIn_RoomNotVacant_SG203_AC2`. Fakes over mocks; injected clock and id generator. Integration tests create their own tenant in a Testcontainers PostgreSQL. Provider contract tests validate real responses against `contracts/openapi.yaml`. Pricing tests read the golden file; property tests print their seed on failure. Coverage gates: docs/08 §3.

## Request limits and flags (SG-203)

- Every request body is capped at 64 KiB (`maxRequestBodyBytes`, middleware in `router.go`): a larger declared length or a longer chunked stream ends as 413 `PAYLOAD_TOO_LARGE` before any handler or use case.
- With a feature flag off, request binding still runs first: a missing or malformed `Idempotency-Key` or a malformed body answers 400 `BAD_REQUEST` before the 404 `FEATURE_DISABLED`. No use case or database I/O happens in either case.
